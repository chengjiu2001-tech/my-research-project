# API 流量看板 · 第一版设计方案

版本：v1.0；日期：2026-10-27（Asia/Shanghai）。

本文件将本次对话上一轮提出的方案确认为项目第一版设计基线。以下为该方案的结构化归档；原定架构为完整产品目标，本次实现的取舍与完成情况见 review-and-scope.md。

## 产品目标

集中查看 DeepSeek、Kimi / Moonshot、OpenAI API 等平台的 Token、费用和余额，按平台、账户、模型、项目及时间分析成本。各平台账单与权限不统一，同时支持官方账单同步和 API 调用记录采集，明确区分官方费用、调用实测与估算。

Codex 按实际使用方式区分：API Key 计费调用归入对应 API 账户；ChatGPT 订阅内 Codex 配额单独处理，不能直接作为 API Token 账单。

## 页面

1. 总览：本月/今日费用、输入/输出/缓存 Token、请求数、成功率、预算使用率、平台余额、每日趋势、平台分布、模型排行、同步状态。
2. 用量分析：按平台、账户、模型、项目、Key 标签、日期过滤；请求/失败数、平均耗时、单次成本、CSV 导出。网页不展示完整密钥。
3. 费用账单：官方费用、估算费用与差异；保存原币，汇总换算注明汇率、日期。
4. 预算提醒：总预算、平台/项目预算，50%/80%/100% 阈值，月末预测。先实现站内提醒，后续扩展外部通知。
5. 账户接入：密钥、同步频率、接入方式、模型价格、成功时间、错误原因。

## 采集架构

- 官方通道：定时读取平台支持的余额、用量、账单，注意管理员权限与更新延迟。
- 调用通道：由 SDK 或统一网关采集响应 usage、模型、项目、耗时等，覆盖已接入调用。
- 适配器 → 标准化/去重 → 数据库 → 费用计算/账单核对 → 查询 API → 网页与预算提醒。
- 两个通道不可直接相加。官方数据用于核对，调用数据用于细分；标明覆盖范围。接入前历史不可获得时明确注明起始时间。

## 数据模型

- provider_accounts：平台、账户、密钥引用、权限、同步状态。
- usage_events：单次请求 ID、平台、模型、项目、时间、输入/输出/缓存 Token、耗时、状态、估算费用与币种、数据来源。
- usage_aggregates：小时/日聚合。
- billing_records：官方费用、币种、账期、来源。
- model_prices：计费维度与生效版本。
- projects、budgets、sync_jobs：项目、预算、同步及重试。

未知 Token 字段保存为 null，不把未知填成 0。

## 计费口径

费用 = 各计费项用量 × 对应生效价格。历史调用使用当时价格；处理缓存包含关系，避免重复收费；reasoning Token 若已包含在输出，不重复累计。流式缺少最终 usage 时标记不完整；分词估算必须标识。业务请求与实际计费重试区分。不同模型的 Token 分词方式不同，成本对比通常更有参考意义。金额使用定点小数。

## 原推荐技术与安全

完整目标架构：Next.js + TypeScript、Tailwind/shadcn、ECharts、服务端 API、PostgreSQL/Prisma、独立定时 Worker、Docker Compose。初期单体部署，分析任务增多后才考虑 Python 服务或微服务。

服务端保存密钥，前端只调用自己的后端；优先使用最小权限凭据；完整部署设计中密钥加密且主密钥与数据库分离；默认不存提示词与回答，日志屏蔽密钥；个人公网部署也需要登录与 HTTPS。

## 阶段与验收

1. 核验平台接口和权限，确认 Codex 计费来源，产出接入能力表。
2. MVP：账户管理、每日用量、费用趋势、平台/模型筛选、手动/定时同步、CSV。验收：重复同步不重计；来源与时间可见；官方/估算分开；未知不显示为零。
3. 细分：SDK/网关、项目、缓存分析、预算、账单差异。
4. 团队：多用户、部门预算、审计。

预测先使用近期日均用量，异常分析先使用同星期历史分布；积累足够数据后再引入复杂模型。
